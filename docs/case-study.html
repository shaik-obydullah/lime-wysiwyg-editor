Case Study: Building Lime WYSIWYG Editor — A Zero-Dependency Rich Text Editor with MySQL Persistence

Published by shaik-obydullah · Part of the Lime family of open-source tools · v1.0.0 · MIT License

Overview

Lime WYSIWYG Editor is a self-contained, browser-based rich text editor built with vanilla JavaScript and the HTML5 contenteditable attribute. It ships with a full formatting toolbar, a WordPress-style image uploader, and a PHP/MySQL backend so documents — including embedded image URLs — persist across sessions.

The entire project is about one screen: an editor pane where a user can format text, drop in images, save a document with a title, and reload it later. It is deliberately small, dependency-free on the frontend, and packaged for Docker so it runs with a single command.

The Problem

Many teams reach for heavyweight editor frameworks (TinyMCE, Quill, CKEditor, ProseMirror) for what is often a simple requirement: a reliable "write and save" text area. Those libraries bring:

  • Large bundle sizes — hundreds of KB (or MB) of JavaScript before a single character is typed.
  • Build tooling overhead — webpack, Vite, React/Vue integrations, node_modules sprawl.
  • Proprietary or dual-licensing considerations for commercial projects.
  • Complexity that exceeds the need — collaborative editing, custom schemas, and plugin ecosystems most projects never touch.

Meanwhile, the native browser primitives — contenteditable and the (sadly deprecated but still universally supported) document.execCommand() API — are capable of covering the 80% case for formatting rich text in a fraction of the code. The goal of this project was to prove that a genuinely useful editor can be built with zero frontend dependencies, a tiny PHP API, and one MySQL table.

Goals

  1. Deliver a full-featured formatting toolbar using only native browser APIs.
  2. Persist documents (HTML + title) to MySQL with a minimal REST-style API.
  3. Handle image uploads the way WordPress does — local file picker to server to URL.
  4. Keep the attack surface small with real MIME validation and script-blocking.
  5. Provide a one-command Docker setup for editor + database + admin tool.
  6. Stay under ~300 lines of JavaScript for all editor logic.

Architecture

The application follows a deliberately simple three-tier structure:

browser (index.html + editor.js)
   │  fetch() JSON
   ▼
PHP endpoints (save.php, load.php, list.php, upload.php)
   │  PDO / filesystem
   ▼
MySQL (documents table)  ·  uploads/ (image files)

Frontend. index.html defines the layout: a toolbar of grouped buttons, a document bar (title input, saved-document dropdown, Load/New/Save buttons), the contenteditable content area, and a status bar with live word/character counts and an HTML-View toggle. editor.js wires it together: every toolbar button carries a data-cmd attribute that maps to a document.execCommand() call, so adding a new formatting button is a one-line change in HTML with no JavaScript.

Backend. Each PHP file is an endpoint. db.php opens a PDO connection from environment variables and self-creates the documents table on first request — there is no migration step. save.php does an UPDATE or INSERT depending on whether a document id is present. load.php returns a specific document or the most recently updated one. list.php returns id/title/updated_at pairs for the dropdown. upload.php validates and stores images.

Data model. Following the WordPress model, MySQL stores only the HTML content with <img src="..."> references; the actual image bytes live in the uploads/ directory. The schema is a single table:

documents (
  id         INT AUTO_INCREMENT PRIMARY KEY,
  title      VARCHAR(255) NOT NULL DEFAULT 'Untitled',
  content    LONGTEXT NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
)

Key Features

  • Full formatting toolbar — undo/redo, headings (H1–H3, paragraph, code block, blockquote), bold/italic/underline/strikethrough/superscript/subscript.
  • Typography — font family and size dropdowns, text color and highlight color pickers.
  • Lists & alignment — bullet/numbered lists, indent/outdent, left/center/right/justify.
  • Links & media — insert/remove links via prompt, WordPress-style image upload, horizontal rule.
  • Document management — title input, saved-document dropdown, Load/New/Save, auto-timestamps.
  • HTML View — toggle between rich text and raw HTML, so power users can hand-edit markup before saving.
  • Live stats — real-time word and character counts.
  • Keyboard support — Ctrl+B/I/U, Tab inserts an indent, shortcuts driven natively by the browser.

Design Decisions Worth Noting

1. Zero-dependency frontend

There is no build step, no package.json, no node_modules. editor.js is a single IIFE (~290 lines) that talks to the DOM directly. Deployment is copying files onto a web server. This makes the project trivially auditable and maintainable.

2. Toolbar driven by data attributes

Buttons are declarative: <button data-cmd="bold">. A single event listener on the toolbar reads data-cmd, executes the command, then refreshes toolbar state and stats. The active-state highlighting is handled generically with document.queryCommandState() and document.queryCommandValue(), keyed off a small list of toggle commands.

3. WordPress-style image pipeline

The image button creates a hidden file input, posts the file as multipart/form-data to upload.php, and on success inserts the returned absolute URL into the document with execCommand('insertImage', false, url). This mirrors how WordPress handles media and keeps the DB small.

4. Self-bootstrapping schema

db.php runs CREATE TABLE IF NOT EXISTS on every connection. First run "just works" — there is no separate schema.sql to apply.

5. HTML view via element swap

Toggling HTML View copies innerHTML into textContent (and back), a simple and safe way to show the raw markup without a textarea or extra editor state.

Security Measures

  • Real MIME validation — uploads are checked with mime_content_type(), not the client-supplied type, and restricted to jpg, png, gif, webp, svg, and bmp.
  • Size limit — files larger than 2 MB are rejected with HTTP 413.
  • Script execution blocked — uploads/.htaccess denies execution of PHP/scripts inside the uploads folder, and file names are server-generated with uniqid() so nothing user-supplied becomes a path.
  • SQL injection resistant — all queries use PDO prepared statements.
  • Honest limitation — content is stored as raw HTML and rendered via innerHTML by design. The README clearly warns that the editor is intended for trusted users and that content must be sanitized server-side before being shown on public pages.

Challenges & Solutions

Browser inconsistencies in execCommand

document.execCommand() is formally deprecated and behaviors vary between browsers. The solution was to stick to well-tested commands, keep the toolbar state synced on every selection change (via the selectionchange event), and treat the editor as a best-effort rich text surface with an HTML view as the escape hatch.

First-boot MySQL readiness

MySQL takes several seconds to initialize its data directory, while Apache starts immediately. A Docker healthcheck on the database combined with depends_on: condition: service_healthy handles ordering, and the README documents the "wait and run compose up again" fallback for edge cases.

Uploads directory permissions

Apache needs write access to uploads/, which differs between Docker and bare-metal setups. The Docker entrypoint creates the directory and chowns it to www-data on every container start, removing a common source of runtime failures.

Tab key trapped inside the editor

By default Tab moves focus out of the content area. Intercepting the keydown event and calling execCommand('insertHTML', ' ') keeps the tab as an indentation key while typing.

Results

  • ~290 lines of JavaScript implement the entire editor interaction — no framework, no build step.
  • 4 PHP endpoints totaling under 140 lines provide full CRUD + uploads.
  • Zero frontend dependencies; the only server-side extension required is PHP pdo_mysql.
  • One-command deployment — docker compose up -d --build brings up the editor on :8080, MySQL, and Adminer on :8081.
  • Single-table persistence with automatic creation, timestamps, and a WordPress-compatible content model.

How to Run It

git clone https://github.com/shaik-obydullah/lime-wysiwyg-editor.git
cd lime-wysiwyg-editor
docker compose up -d --build

Editor: http://localhost:8080  ·  Adminer: http://localhost:8081

Prefer no Docker? Requires PHP 8.3+ with pdo_mysql and MySQL 8.0:

mysql -u root -p -e "CREATE DATABASE wysiwyg CHARACTER SET utf8mb4;"
DB_HOST=127.0.0.1 DB_NAME=wysiwyg DB_USER=editor DB_PASS=editor_pass \
  php -S localhost:8080

API Reference

Endpoint Method Description
save.php POST Save/update a document. Body: { "id"?: int, "title": string, "content": string }. Returns { success, id }.
load.php GET Load a document. ?id=N loads a specific one; without id returns the latest.
list.php GET List all documents: { id, title, updated_at }[].
upload.php POST Upload an image (multipart field image). Returns { success, url }.

Conclusion

Lime WYSIWYG Editor demonstrates that a production-usable rich text editor does not require a framework or a build pipeline. By leaning on contenteditable, document.execCommand(), a handful of thin PHP endpoints, and a single MySQL table, the project delivers the everyday 80% of editing — formatting, media, and persistence — in a codebase small enough to read in one sitting. It is MIT-licensed, Docker-ready, and designed as part of the Lime family of open-source tools.
